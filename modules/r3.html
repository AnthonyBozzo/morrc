R3. Data management and REDCap

Most errors in resident research are made at data collection, not analysis. Build a clean REDCap database, handle missing data properly and keep patient data secure.

Learning objectives

By the end of this module you will be able to:

  • Build a REDCap project with a data dictionary and validation.
  • Apply data security and privacy standards for health data.
  • Plan data cleaning, missing data and version control.
  • Write reproducible analysis code (R, Stata or Python).

Prerequisites: F5 and R2. Not locked: you can start here.

Why this matters to youA well-built data dictionary saves weeks of cleaning and is part of your R4 capstone. Poor data handling is also the commonest privacy breach in resident research.

1. Plan before you collect

  • Write a data management plan: what is collected, by whom, where it is stored, who can access it, how long it is kept and how it will be shared.
  • Collect only what the protocol needs (data minimization, F5). Each variable should map to an objective, a confounder or eligibility.
  • Build and pilot the database on 5 to 10 charts before full data collection. Fix the dictionary, then lock its structure.
  • Use double data entry or a re-abstraction audit of a random sample (e.g., 10%) to estimate the error rate.

2. REDCap

REDCap (Research Electronic Data Capture; Harris et al., 2009) is a secure, web-based platform used by thousands of institutions. Features that matter for resident projects:

  • Field validation (integer, date, ranges) and required fields, which catch errors at entry.
  • Branching logic (show “revision reason” only if revision = yes) and calculated fields.
  • Longitudinal events and repeating instruments for follow-up visits.
  • Surveys for PROMs, including automated invitations, and e-consent where the REB approves it.
  • Audit trail, user rights and data access groups for multicentre projects.
  • A shared instrument library containing many validated questionnaires (check licensing).

3. Building a good data dictionary

  • Variable names: short, lowercase, no spaces, and meaningful (oxford_hip_6m, not Q7).
  • One concept per variable, and coded categories (radio or dropdown) rather than free text for anything you will analyze.
  • Units in the label (kg, mmol/L, hours) and validation ranges matching the instrument (the Oxford Hip Score runs from 0 to 48).
  • Missing data: don't type 999 into a numeric field, because it will be averaged as a real value. Leave the field empty and record the reason (REDCap supports missing-data codes), so “not collected” is distinguished from “patient declined” or “died”.
  • Identifiers: keep names, MRNs and RAMQ numbers out of the analysis database, or in a separate, restricted instrument, as approved by the REB. Use a study ID.
  • Dates: use date-validated fields. Derive intervals (time to surgery) by calculation, not by hand.

4. Data cleaning without regret

  1. Never edit the raw export. Keep it read-only; clean with a script (R, Stata, SAS or Python), so every change is reproducible (Wilson et al., “Good enough practices”, PLoS Comput Biol 2017).
  2. Run range checks (age, scores), logic checks (surgery before admission? PROM recorded after death?) and duplicate checks (repeated study IDs).
  3. Send queries back to the source (the chart) rather than guessing, and record the resolution in a cleaning log.
  4. Lock the database before the primary analysis, and keep the analysis code with the paper's materials.

5. Missing data

Mechanism (Rubin 1976)MeaningExampleConsequence
MCAR: missing completely at randomMissingness is unrelated to any dataA batch of questionnaires lost in the mailComplete-case analysis unbiased (but less precise)
MAR: missing at randomRelated to observed variablesOlder patients less likely to return PROMs, and age is recordedMultiple imputation using those variables can correct bias
MNAR: missing not at randomRelated to the unobserved value itselfPatients with poor outcomes stop attendingNo standard method is unbiased; sensitivity analyses are essential
  • Prevention beats cure: short instruments, flexible follow-up windows, multiple contact methods, and recording the reason for every missing value.
  • Multiple imputation creates several plausible completed datasets and combines the results. Sterne et al. (BMJ 2009) describe its potential and pitfalls; include the outcome and auxiliary variables in the imputation model.
  • Death is not missing data to be imputed. A PROM “after death” doesn't exist, so use composite outcomes or methods that handle truncation by death, and report deaths separately.

6. Security and storage

  • Store data only on institution-approved platforms (REDCap, hospital network drives). Never use personal email, personal cloud accounts, USB keys or unencrypted laptops.
  • Keep the linking key separate from the coded data, with restricted access.
  • Share data outside the team only under REB approval and a data-sharing agreement.
